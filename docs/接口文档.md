# 接口文档（前端对接用）

> 「陪着」/「微光同行」后端 v0.1.0
> 基础接口按模块列出。24 稿合并增量见文末；可控记忆与私密草稿详见 [陪伴核心接口契约.md](陪伴核心接口契约.md)。所有接口都返回同一种形状，前端只需判断 `code === 0`。

---

## 一、先看这五条约定

### 1. 后端地址

开发时后端跑在 `http://127.0.0.1:3000`，接口前缀统一是 `/api`：

```
http://127.0.0.1:3000/api/auth/login
```

> 如果前端是用 `file://` 直接打开的（双击 html），浏览器会因跨域拦掉请求，
> 请用本地静态服务打开（VSCode Live Server / `npx serve` 都行），
> 或者直接在 `api.js` 里写死后端地址。

### 2. 登录令牌怎么带

登录成功后拿到 `token`，之后每个请求放到请求头：

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

需要登录的接口没带 token 会返回 `40100`。

### 3. 统一的返回形状

```json
成功：{ "code": 0, "msg": "ok", "data": { ... } }
失败：{ "code": 40100, "msg": "请先登录", "data": null }
```

**前端只需要判断 `code === 0`**，其它都是失败；`msg` 可以直接弹给用户看。

### 4. 错误码 = HTTP 状态码 × 100

| code | 对应 HTTP | 含义 | 前端怎么处理 |
|---|---|---|---|
| `0` | 200 | 成功 | — |
| `40000` | 400 | 参数错误 / 校验失败 | 弹 `msg`，留在当前页 |
| `40100` | 401 | 未登录或令牌过期 | 清 token，跳登录页 |
| `40300` | 403 | 没权限 / 被禁言 / 拉黑 | 弹 `msg` |
| `40400` | 404 | 资源不存在（**别人的私密日记也走这个**） | 提示"内容不存在" |
| `40900` | 409 | 冲突（如今天已经写过日记） | 弹 `msg` |
| `42900` | 429 | 操作太频繁 | 弹 `msg`，稍后再试 |
| `50000` | 500 | 服务器错误 | 提示稍后再试 |

> 注意：私密日记不是返回 403，而是 **404** —— 故意让"没权限"和"不存在"
> 看起来一样，不泄露"这篇日记存在但你无权看"。

### 5. 分页

列表接口统一支持 `page` / `size`，返回：

```json
{
  "list": [ ... ],
  "page": 1,
  "size": 20,
  "total": 57,
  "hasMore": true
}
```

`hasMore` 是后端算好的，前端不要自己用 `total` 推。

## 二、几个容易踩的点

**图片地址**
后端返回的头像 / 配图是**完整 URL**（形如 `http://127.0.0.1:3000/uploads/xxx.jpg`），
直接用 `<img src>` 即可，不要再拼域名。

**时间格式**
统一是 `"YYYY-MM-DD HH:MM:SS"` 字符串（不是时间戳），直接显示就行。

**上传头像**
两个接口任选：`POST /api/user/avatar`（multipart，字段名 `file`）
或 `POST /api/user/avatar-base64`（JSON，`{ image: "data:image/png;base64,..." }`）。
单个文件上限 5MB。

**AI 聊天是流式的吗**
不是。`POST /api/ai/chat` 一次性返回整段回复，直接渲染即可。
返回里可能带 `care` 字段（检测到情绪危机时），里面是热线列表，
建议单独渲染成一张卡片，不要混在气泡里。

**禁言**
群发消息被禁言时返回 `40300`，`msg` 里会带剩余时间。

## 三、接口清单

**登录** `/api/auth`

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/send-code` | 发送验证码 `{phone}` |
| POST | `/api/auth/login` | 登录（新号自动注册）`{phone, code}` → `token` |
| POST | `/api/auth/register` | 显式创建账号 `{phone, code, nickname}` → `token`（手机号已注册返回 409） |

> **单点登录（按设备）**：登录时前端带 `deviceId`（localStorage 里的随机串）。
> **换一台设备登录**会把旧设备顶下线（旧 token 下一次请求收到 401「账号已在别处登录」）；
> **同一台设备重新登录 / 刷新页面不会踢自己**。不带 `deviceId` 的调用（脚本、curl）不做限制。
| GET | `/api/auth/me` | 用 token 换当前用户信息 |
| POST | `/api/auth/logout` | 退出 |

**漂流瓶** `/api/bottle`

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/bottle/toss` | 扔一个瓶子 `{content, isAnon}` |
| GET | `/api/bottle/sea?size=` | 捞几个（**自动排除我捞过的**） |
| POST | `/api/bottle/pick/:id` | 标记"我捞到了"（幂等） |
| GET | `/api/bottle/mine` `picked` | 我扔过的 / 我捞到过的 |

| DELETE | `/api/bottle/:id` | 收回自己扔的 |

**一个瓶子可以被多人捞到**（不是"谁先捞到归谁"）。
理由：一条温暖的留言被 10 个人看到，比只被 1 个人看到要好。
默认匿名，匿名时作者显示为"一个陌生人"。

**群聊** `/api/group`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/group/rooms` | 4 个房间（含人数、未读数、禁言状态） |
| POST | `/api/group/rooms/:key/join` | 进房间（key 可以是 code 或 id） |
| GET | `/api/group/rooms/:key/messages` | 取消息（`before` 翻历史 / `limit` / `markRead`） |
| POST | `/api/group/rooms/:key/messages` | 发言（**机器人在这里干活**） |
| POST | `/api/group/rooms/:key/read` | 手动标记已读 |
| GET | `/api/group/rooms/:key/members` | 群里的人 |
| GET | `/api/group/my-rooms` | 我进过的群 |
| GET | `/api/group/total-unread` | 所有群的总未读（红点用） |
| POST | `/api/group/_test/reset` | **仅开发环境**：重置机器人的违规计数 |

4 个房间（存在 `chat_rooms` 表，code 固定）：

| id | code | 名字 | 分类 |
|---|---|---|---|
| 1 | `age` | 同龄群 | 按年龄段 |
| 2 | `interest` | 拾趣 | 按兴趣 |
| 3 | `province` | 同省群 | 按省份 |
| 4 | `zodiac` | 星迹 | 按星座 |

房间是**固定的 4 个**，用户不用创建 —— 像微信群一样，点进去就在里面。
第一次发言会自动入群。

**未读数的机制**：`chat_members.last_read_id` 记着"我读到哪条了"，
看消息时自动推到最新。所以不需要前端自己算。

**私信** `/api/message`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/message/conversations` | 会话列表（含未读、最后一条、拉黑状态） |
| GET | `/api/message/total-unread` | 总未读（红点用，永不抛错） |
| POST | `/api/message/open` | 打开和某人的会话 `{userId}` 或 `{uid}` |
| GET | `/api/message/with/:userId` | 和某人的聊天记录 |
| POST | `/api/message/send` | 发私信 `{toUserId, content}` 或 `{convId, content}` |
| POST | `/api/message/read/:userId` | 标记和某人的会话已读 |
| DELETE | `/api/message/conversation/:convId` | 删除会话（只从我这边消失） |
| POST | `/api/message/block` | 拉黑/取消拉黑（切换）`{userId}` |
| GET | `/api/message/blocked-list` | 我拉黑过的人 |

**★ 私信的三个关键设计 ★**

1. **一对人只有一行会话**。表里用 `(user_a, user_b)` 唯一索引，并且约定
   `user_a < user_b`。所以每次都要先把两个 id 排序再查 —— 不这么做的话，
   A→B 和 B→A 会落成两行，两个人各自只看到一半对话。
   （这是私信功能最常见的实现错误，所以专门写了测试。）
2. **被机器人拦下的消息会留痕**（`messages.status='blocked'`）。
   不发给对方，但存进数据库：
   - 发件人自己能看到"这句话没发出去"（前端标灰 + 删除线）
   - 管理员能追溯"这个人试图发广告"
   只拦不存的话，出了问题查不到。
3. **拉黑是必须有的**。私信是最容易被骚扰的地方。被拉黑的一方
   会收到一句含糊的提示（"消息发送失败，对方可能不想收到消息"），
   而**不会**被告知"你被拉黑了" —— 说明白了会让人反复试探。

其他规则：1.2 秒发送频控（防连点）、危机信号返回 `care` 关怀提示。

**发现页推荐流** `/api/discover`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/discover` | 推荐流（`size` / `page` / `type`） |
| GET | `/api/discover/stats` | 推荐池里有多少内容 |

返回的是**混合内容**，每条带 `type`：

```json
{ "list": [
    { "type": "diary",  "diary":  { ... } },
    { "type": "user",   "user":   { ... } },
    { "type": "bottle", "bottle": { ... } }
] }
```

**★ 这和"时间线"是两回事 ★**

原来的实现是按时间倒序取全部公开日记 —— 那是个时间线，不叫推荐。
真正的推荐要做到：

1. **是陌生人的**（已关注的人在关注流里，不重复推）
2. **随机但翻页不重复**
3. **不推自己**（自己的内容在"我的主页"里）
4. **绝不推私密日记**（这是最严重的一类 bug）

**实现方式**（踩过坑才定下来的）：

| 问题 | 错误做法 | 正确做法 |
|---|---|---|
| 怎么随机 | `ORDER BY RAND()` → 翻页重复、遗漏 | 用"按时间变化的固定种子"做哈希排序，10 分钟换一批 |
| 怎么混排 | 只按哈希排 → 数量多的类型会连成一片 | 按类型**轮流取**（diary→bottle→user 循环） |
| 排序算式 | `MOD(id * 种子, 质数)` → **几乎不随机**（id 远小于质数，结果单调） | MurmurHash3 的收尾函数，真正打散 |

第三条是实测发现的：用 `MOD(id * 种子, 1000003)` 时，
5 篇日记 + 3 个瓶子 + 2 个人排出来是 `131,130,129,128,127` ——
基本就是 id 倒序，又绕回时间线了。换成真哈希后，
相邻 id 的排名变成 `82795892 / 2906772836 / 979051624 / …`，才真正打散。

**为什么排序在应用层做**：在 SQL 里复现这个哈希要用位移 + 异或 + 大数相乘，
MySQL 的 BIGINT UNSIGNED 还容易溢出。而推荐池数据量很小，
一次全取回内存排序完全没问题 —— 那就选能保证正确的那条路。

**拉黑过的人互相不推荐**：如果对方拉黑了我还推给我，
点进去会发现发不出消息，体验很差。

**AI 聊天** `/api/ai`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ai/status` | 当前用的哪个模型（没配 Key 时告诉前端是体验版） |
| POST | `/api/ai/chat` | 说一句话 `{message}` → `{userMessage, reply, saved, care, memoryUpdated}` |
| GET | `/api/ai/messages` | 历史记录（**换设备续聊靠这个**） |
| GET | `/api/ai/greeting` | 打开聊天页时的开场白（有记忆时会体现） |
| GET | `/api/ai/memory` | 看 AI 记得我什么 |
| DELETE | `/api/ai/memory` | 忘掉我（清空记录 + 记忆） |

**★ 为什么 Key 必须放在服务器 ★**

原来 `chat.html` 里有三行：

```javascript
const API_KEY = "sk-...";            // ← 一个真实的 Key 写死在源码里
const API_URL = "https://...";
const MODEL = "deepseek-chat";
```

浏览器拿着它直接调大模型。**前端代码是公开的** —— 任何人
"查看网页源代码"就能把 Key 复制走，用光你的余额。

现在改成：浏览器 → 我们的后端（持有 Key）→ DeepSeek。
Key 只在服务器的 `.env` 里（权限 600），前端一行都拿不到。
自检里加了**两条硬性检查**：前端目录不能出现 `sk-` 开头的字符串、
不能出现大模型服务商域名（连注释里都不允许）。

**★ "记忆"拆成两层 ★**

| 层 | 存在哪 | 作用 |
|---|---|---|
| 短期记忆 | `ai_messages` 表最近 N 条 | **换设备登录能拉到历史**（这就是需求里"同一个号换一个设备还能继续聊天"） |
| 长期记忆 | `ai_profiles.summary` 一段摘要 | 聊很久之后只带"摘要 + 最近几轮"，token 不会越滚越多 |

摘要用 **消息 id 当游标**（`summary_until_id`，"已压到哪条"）。
不用条数当游标的原因见坑 21 —— 那会丢掉中间的内容。

**★ 用户能看到、也能删掉记忆 ★**

`GET /api/ai/memory` 会返回"AI 记得你什么"，`DELETE /api/ai/memory`
一键清空。一个陪伴产品偷偷记着你说的话却不让你知道，是不对的。

**★ 没配 Key 时会降级，不会报错 ★**

`DEEPSEEK_API_KEY` 没填时，后端自动切到内置的"体验版陪伴者"：

- 它不会真的理解你说的话（没有大模型）
- 但它会认真回应、会记得你之前说过的事、会在你说难受时给关怀热线
- 前端会拿到 `provider: 'local'` 和一句说明，**明确告诉用户这是体验版**（不假装是大模型）

这样"聊天记录落库 / 换设备续聊 / 长期记忆"这些功能现在就能完整验证，
Key 一到只需往 `.env` 里填一行、重启服务，代码一行都不用改。

`PATCH /api/user/me` 可改字段与**自动推导**规则：

| 字段 | 说明 |
|---|---|
| `nickname` | 昵称，1-32 字，**不能和别人重名** |
| `uid` | 对外 ID，6-16 位数字，**不能和别人重名** |
| `signature` | 个性签名，最多 255 字 |
| `addr` | 地址，最多 64 字 → **自动推出 `province`**（同省群要用） |
| `birthYear` + `birthMonth` + `birthDay` | → **自动算出 `zodiac`**（星迹群要用）和 `age`/`ageGroup` |
| `gender` | `unknown` / `male` / `female` |
| `cover` | 主页背景图 |

**清空字段的写法**：传 `null` 或 `''` 就是清空。

| POST | `/api/interact/notifications/read` | body `{ ids: [...] }` 或 `{ all: true }`，返回 `{ unread }` |
| — | 通知 `type` 共 7 种：`like` 点赞 / `favorite` 收藏 / `comment` 评论 / `mention` @提到 / `reply` 回复 / `bless` 祝福 / `message` 私信与转发。祝福和私信类 `diaryId = null`，前端据此决定点哪跳哪 |

> 规则：自己互动自己不生成；赞/收藏同一人对同一篇只留一条（重复只刷新时间）；评论每条都记。

### 现在的规模

基础说明包含十九稿兼容层；实际接口与表结构还包含后续参赛核心及下述合并增量。

### 24 稿合并后的接口增量

- `GET /api/interact/friend-stats`：登录用户的 `{friends, fans, following}`；friends 仅计互关。
- `GET /api/interact/my-follows?mutual=1`：互关筛选，列表含 `isMutual`；`total` 和 `hasMore` 对应筛选结果。
- `GET /api/interact/my-fans`：返回 `list`、真实 `total`；每人含 `isFollowedBack`、`fans`、公开 `diaryCount`、省份。当前最多 50 人。
- 日记列表/详情统一增加 `saves`（实际收藏记录数）；评论接口的 `commentCount` 用于提交后的即时计数。
- 评论 @ 和祝福提醒投递至私信，会话未读只增加接收方；自动提醒失败不撤销已经保存的评论或祝福。@ 提醒仅带通用提示及链接，不复制日记/评论正文。
- 消息跳转仅支持 `\n[跳转] diary-public.html?id=<正整数>` 和 `\n[跳转] bless-sent.html?type=received`；其他内容作为纯文本。
- `POST /api/report` 检查目标可见性；私信仅允许举报本人收到的正常非系统消息。`GET /api/report/mine` 增加 `targetInfo`（作者、摘要、时间等），内容当前不可访问时返回 `null`。
- 私信拦截返回 `blocked`、`bot`、`botNotice`、`violationCount`；`care` 独立于发送成功/失败，前端应优先展示。纯危机求助可通过群禁言/私信频控，混合违规仍拦截并提供关怀。
