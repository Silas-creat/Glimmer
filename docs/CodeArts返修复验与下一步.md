## 仍需收尾的六项

### R1 · P1 · 草稿生成没有在发送前重新核对账号

- 位置：`前端参考/chat-companion.js:693`，关联 `前端参考/api.js:60`。
- 场景：A 已选好本人材料；同源其他页面将当前凭证换成 B，旧页面的 storage 处理尚未执行；此时点击“生成草稿”。
- 结果：prepare 直接读取旧页面 A 的材料，共用 API 从当前 storage 取得 B 的凭证。隔离脚本已证明页面 uid 仍为 A、当前 token 已为 B，且请求正文带 A 的材料；实际服务端归属由 B 的鉴权决定。
- 影响：跨账号材料隔离存在窗口，不能只依赖 storage 事件及时到达。此处为代码路径和可控事件顺序验证，未声称真实浏览器中发生过泄露。
- 修复要求：草稿入口发请求前检查身份，材料与请求绑定同一账号/代次；若身份变化，应清空旧材料、停止该次动作，让新账号重新选择。确认、取消和自动恢复也核对所属账号，不能将旧编辑内容随新的凭证发送。

### R2 · P1 · 清除成功后仍能重新显示旧摘要

- 位置：`前端参考/chat-companion.js:593`，关联记忆读取回调 `:542`。
- 场景：DELETE 清除未完成 → 关闭清除弹层、打开记忆，GET 得到清除前快照但迟迟未返回 → DELETE 成功 → GET 最后返回。
- 结果：页面已经提示清除成功，旧摘要又被写入 `memorySnapshot` 并展示。没有证据表明该响应把摘要写回数据库；已确认的是前端残留内容重新出现。
- 根因：清除成功未使期间发出的记忆读取失效；现有测试只覆盖“先读记忆，再打开清除”的相反次序。
- 修复要求：同账号清除成功使此前历史/记忆读取失效；新面板显示准确状态。身份代次与面板代次应分开处理，避免清除旧账号响应影响新账号，也避免粗暴清空无关草稿编辑面板。

### R3 · P2 · A 的迟到清除响应清空 B 当前页面

- 位置：`前端参考/chat-companion.js:593` 至 `:607`。
- 场景：A 清除等待响应 → 正常触发 storage 换到 B → B 开始新对话 → A 的清除成功最后到达。
- 结果：成功回调无条件替换当前 session、清掉 B 的气泡和临时上下文，并错误提示“已清除本人聊天记录和摘要”。**不是 B 的数据库记录被 A 删除。**
- 修复要求：清除动作绑定发起时账号和操作代次，身份变化后不再更新新账号页面；同账号关闭面板后，仍要正确处理其旧上下文失效，不能仅加一个面板检查就提前返回。

### R4 · P2 · 旧聊天请求解除新请求的发送锁

- 位置：`前端参考/chat-companion.js:1047` 至 `:1051`。
- 场景：旧请求等待 → 清除成功并立即发送新消息，新请求仍等待 → 旧请求先返回 → 再发第三条。
- 结果：旧 `finally` 把 `sending` 改为 false、启用按钮。第三条加入气泡/日记候选材料，但 helper 仍忙，实际没有发出第三次请求，页面又出现“正在回复”。
- 修复要求：发送状态绑定当前发送操作，旧请求只清理自己的提示，不释放新请求的锁；发送前身份检查与锁的获取也要防止重复进入。

### R5 · P2 · 确认日记返回的关怀仍在弹层后面

- 位置：`前端参考/chat-companion.js:928` 至 `:929`，关联 `renderConfirmSuccess:840`。
- 场景：普通草稿经过用户编辑后包含危机内容，confirm 返回日记保存结果和 care。后端 `src/utils/companion.js:97` 的 `confirmResult()` 确实会返回该 care。
- 结果：前端只调用背景 `showCare()`，保存成功弹层没有关怀正文和热线。之前 B4 修复只覆盖 prepare 的 `draft:null` 分支。
- 修复要求：在成功弹层显示完整 care 与安全支持链接，并覆盖幂等恢复成功的同类返回；不改变现有后端确认语义，不伪造关怀内容。

### R6 · P3 · “停止生成”后仍能反复生成并重复追加关怀

- 位置：`前端参考/chat-companion.js:725`、`:733` 至 `:737`。
- 场景：prepare 返回 care 且 draft 为 null。
- 结果：按钮先被重新启用，原表单仍可点“生成草稿”；反复请求并追加相同关怀块。后端仍阻止生成该草稿，不是误存日记问题。
- 修复要求：该轮进入明确停止状态，保留关怀与关闭/返回选择入口；不要保留仍可重复点击的生成按钮。
